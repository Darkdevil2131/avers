# Security boundary

Credentials are distinct, named, at least 32 characters, supplied through environment configuration, hashed for constant-time comparison, and absent from repository files. The frontend retains tokens only in memory. All project resources authorize membership; owners manage membership and read audit logs, editors write, viewers read. The 512 KiB body limit and 60 writes/searches per minute per authenticated user bound ordinary requests. Source text is untrusted data and rendered as escaped React text. CSP restricts script and connection origins. Source provenance links allow only HTTP(S).

No arbitrary network fetch, shell execution, PDF parser, pickle loader, model tool calling, or cross-project retrieval exists. A local inference subprocess receives only bounded question/evidence data and a local model path; configured API credentials are excluded from its environment. It has no agent tools. This is process separation and a timeout, not a full OS sandbox. SQL uses bound parameters, and FTS terms are sanitized. Snapshots and audit records have SQLite and PostgreSQL triggers preventing ordinary UPDATE/DELETE operations. Database administrators can alter the database; these controls are not cryptographic tamper proofing.

Current deployment scope is a private hosted workspace. Before public production: add TLS termination, secret rotation/session lifecycle, ingress rate limits for invalid authentication, storage quotas, persistent encrypted volumes, operational monitoring, abuse testing, and stronger concurrent/multi-instance isolation. The current app is not approved for sensitive medical or regulated data.

ONNX telemetry is disabled before imports using ORT_DISABLE_TELEMETRY=1, with HF_HUB_DISABLE_TELEMETRY=1 and DO_NOT_TRACK=1. The initial unsafe default was blocked during development. Model preparation downloads public weights explicitly; serving uses local files only. The reasoner preparation script checks the expected GGUF SHA-256. Embedding artifact hashes version the vector cache.

PostgreSQL migration creates restricted ares_app and ares_worker roles. Runtime rejects superuser, RLS-bypass, and source-table-owner credentials. API principal context is transaction-scoped after authentication. RLS protects project data even when application queries omit project predicates. The worker can process jobs across projects and must be treated as a trusted service; its DSN must never reach the browser. Migration administrator credentials must never be passed to API or worker. These boundaries are tested against a disposable PostgreSQL service, not a public deployment or penetration test.
